# Database Design — US-001 Customer Registration (v2)

Companion to `docs/designs/database/US-001-entity-model.md` (the entity/attribute
model and DTO mapping). This document owns the physical schema: tables, every
explicit constraint, indexes, relationships, schema-initialization approach, and
sensitive-data handling. Authoritative artifact paths:
`docs/workflow/artifact-paths.yaml`.

> **v2 revision note:** full rework, not a terminology pass. v1 was designed
> for H2 + Hibernate/JPA (hand-written `schema.sql`, `ddl-auto=validate`,
> `@Entity`/`@Column` annotations, `GENERATED BY DEFAULT AS IDENTITY`,
> `VARCHAR(n)`, `TIMESTAMP WITH TIME ZONE`). None of that exists in the
> current stack. This version targets SQLite via EF Core, per the rewritten
> `docs/architecture/persistence-conventions.md` (PC-1..PC-9): EF Core
> Migrations instead of hand-written DDL, `IEntityTypeConfiguration<T>`
> Fluent API instead of annotations, `TEXT`/`INTEGER` SQLite type affinity
> instead of `VARCHAR`/`BIGINT`/`TIMESTAMP WITH TIME ZONE`, and the
> already-scaffolded `AppDbContext.SaveChangesAsync` + `IAuditable` override
> (`CustomerPortal/Data/{AppDbContext,IAuditable}.cs`) instead of JPA
> auditing. Business content (columns, constraints, rationale, business-rule
> traceability) is unchanged from v1 where the underlying requirement is
> unchanged.

## 1. Scope

US-001 introduces persistence for exactly one concept: a self-registered
customer account (email + BCrypt password hash + role + enabled flag + audit
timestamps). One new table, `customer`. No foreign keys, no join tables, no
existing schema to change — this Story's migration is the first one in the
project.

Persistence behavior **does** change, so `DB_DESIGN` is applicable (not
`NOT_APPLICABLE`).

## 3. Entity naming reconciliation (resolves spec-review F-6 / API design Q-1)

Unchanged from v1 — this reconciliation is a business/naming decision, not a
stack decision. `business-glossary.md` defines **Customer** ("a person who
owns an account") and **Account** ("technical representation of customer
access credentials") as separate terms. The approved Specification (NFR-4:
"The **Customer** entity declares..."), `persistence-conventions.md` PC-5
(example table `customer`), and the API design (`CustomerResponse`, path
`/api/v1/customers`) all name the persisted concept **Customer**.

**Decision (DB_DESIGN, within its entity-naming authority):** the single
entity is named `Customer`, table `customer`. For US-001 it embodies both
glossary concepts — the customer identity and their access credentials —
because US-001 persists no personal-information / profile data (the
glossary's **Profile** is out of scope, US-003). If a future Story separates
profile data from credentials, `Customer` can be split then; nothing here
forecloses that.

Flagged as a non-blocking finding for `DESIGN_REVIEW` to confirm.

## 4. Table `customer`

### 4.1 Purpose

One row per registered customer account. Created by `POST /api/v1/customers`
(FR-1, FR-5). Read later by authentication (US-002, out of scope here).

### 4.2 Columns

| Column | CLR type | SQLite type affinity | Null | Default | Constraint(s) | Notes |
|---|---|---|---|---|---|---|
| `id` | `long` | `INTEGER` | NOT NULL | generated | `pk_customer` (PK) | Surrogate key. EF Core default value-generation for the sole integer key (`INTEGER PRIMARY KEY AUTOINCREMENT` under SQLite) — PC-3. Never a natural key. No explicit Fluent API needed beyond the key name (§8.2). |
| `email` | `string` | `TEXT` | NOT NULL | — | `uq_customer_email` (UNIQUE) | Stored **already normalized to lowercase** by the service (OD-006:A). `HasMaxLength(254)` = RFC 5321 practical maximum (OD-001:A). SQLite has no enforced `VARCHAR(n)`; the length is an EF Core model-level constraint (PC-4). |
| `password_hash` | `string` | `TEXT` | NOT NULL | — | — | BCrypt output is exactly 60 characters (`$2a$`/`$2b$`/`$2y$`, cost ≤ 31). `HasMaxLength(60)` per PC-9. **Never** stores plaintext. See §7 and the Q-2 resolution below. |
| `role` | `string` | `TEXT` | NOT NULL | `"CUSTOMER"` | `ck_customer_role` CHECK IN (`'CUSTOMER'`,`'ADMIN'`) | Stores the literal role-claim value (SC-2 — `CUSTOMER`/`ADMIN`, **no** `ROLE_` prefix), `HasMaxLength(20)`. Modeled as `string`, not a C# enum, so the persisted value matches the claim value byte-for-byte with no name/converter translation to get wrong (see §6 rationale). US-001 always writes `"CUSTOMER"` (SC-2, BR-006). |
| `enabled` | `bool` | `INTEGER` (0/1) | NOT NULL | `1` (true) | — | Account enabled state (BR-004). US-001 always writes `true` (FR-5, SEC-5). DB default is defensive only; the entity always sets it explicitly. |
| `created_at` | `DateTimeOffset` | `TEXT` (ISO-8601) | NOT NULL | — | — | UTC (BR-007, PC-6). Set by `AppDbContext.SaveChangesAsync`'s `IAuditable` override on insert. **Not reassigned after insert** — enforced by that override, not a database trigger. |
| `updated_at` | `DateTimeOffset` | `TEXT` (ISO-8601) | NOT NULL | — | — | UTC (BR-007, PC-6). Set by the same override; equals `created_at` on insert, refreshed on every `SaveChangesAsync` that modifies the row. |

**Q-2 resolution — final `password_hash` definition:** `TEXT NOT NULL`,
`HasMaxLength(60)`, column name `password_hash` (PC-9, SEC-4). This revises
v1's `VARCHAR(60)`, which was an H2/JPA-specific type name; SQLite's
column-type affinity is `TEXT` regardless of the declared max length — the
60-character bound is enforced at the EF Core model level, not by the SQLite
engine. BCrypt hashes are a fixed 60-character string, so 60 is exact, not a
guess. The `password` **72** limit in the Specification (§6.2) and OpenAPI
(`maxLength: 72`) is the **BCrypt plaintext input limit** — 72 **bytes** of
the pre-hash password (spec-review F-5 / API Q-4) — enforced in request
validation and the service re-check (FR-6), **not** a column concern. The
column only ever holds the 60-char hash.

### 4.3 Constraints

| Name | Kind | Definition | Rationale |
|---|---|---|---|
| `pk_customer` | PRIMARY KEY | `(id)` | PC-3 surrogate key; PC-5 naming. Set via `.HasKey(c => c.Id).HasName("pk_customer")`. |
| `uq_customer_email` | UNIQUE INDEX | `(email)` | BR-001 one account per email; BR-003 one account per customer. Case-insensitivity (BR-002) is satisfied because the service lowercases `email` before both the duplicate check and the insert (OD-006:A). Provides the index for "find by email" (PC-7). Set via `.HasIndex(c => c.Email).IsUnique().HasDatabaseName("uq_customer_email")`. |
| `ck_customer_role` | CHECK | `role IN ('CUSTOMER','ADMIN')` | Defensive: keeps `role` within the glossary's fixed value set (`business-glossary.md` Role) even under a manual write. Set via `.ToTable(t => t.HasCheckConstraint("ck_customer_role", "role IN ('CUSTOMER','ADMIN')"))`. Optional per conventions; `DESIGN_REVIEW` may drop it. |

### 4.4 Indexes

| Name | Columns | Unique | Purpose |
|---|---|---|---|
| `uq_customer_email` | `(email)` | yes | Duplicate-email check (FR-4) and future `FindByEmail` (US-002). PC-7: a UNIQUE index already covers lookup — **no separate `ix_customer_email`**. |

No foreign-key indexes (no foreign keys). No other repository lookup keys in
US-001.

## 5. Case-insensitive uniqueness mechanism (OD-006:A)

- The service normalizes `email` with `.ToLowerInvariant()` **before** the
  existence check and **before** constructing the entity.
- The duplicate check uses the already-lowercased value against a plain
  `Task<Customer?> FindByEmailAsync(string email)` /
  `Task<bool> ExistsByEmailAsync(string email)` repository method.
- The column stores only lowercase values; `uq_customer_email` is a plain
  unique index — no `LOWER(email)` functional index, no database-specific
  collation override (SQLite's default `BINARY` collation is exact-match,
  which is correct here since the value is always pre-lowercased).
- Consequence for tests (`TEST_WRITING`): `Alice@Example.com` and
  `alice@example.com` collide; the second registration returns `409`.

## 6. Relationships

None. `customer` is a standalone table for US-001.

- `role` is modeled as a **`string` column with a CHECK constraint**, not a
  `customer_role` lookup table, and not a C# enum with a value converter.
  The glossary defines Role as a fixed two-value permission group; US-001
  assigns exactly one role per account at creation. `persistence-conventions.md`
  PC-5 mentions `customer_role` only as a *naming* example, not as a required
  table. A `string` column (rather than an enum + converter) was chosen so the
  persisted value is textually identical to the SC-2 role-claim value
  (`"CUSTOMER"`) with no separate enum-member-name-to-claim-value mapping to
  keep in sync; `Security` namespace code compares/assigns the same literal
  strings. Flagged for `DESIGN_REVIEW`.

## 7. Sensitive-data handling

| Data | Column | Rule |
|---|---|---|
| Plaintext password | *(none)* | Never persisted. Exists only on the inbound `RegistrationRequest` DTO (SC-1, SEC-3, BR-005). |
| Password hash | `password_hash` | BCrypt hash only (`BCrypt.Net-Next`). Never logged, never returned by any endpoint, never placed on a response DTO (SC-1, PC-9, SEC-4). Excluded from any entity `ToString()` override. Absent from `CustomerResponse` (OD-004:A). |
| Email (PII) | `email` | Stored normalized (lowercase). Not a secret, but not emitted in error messages (SC-9) beyond the standard `fieldErrors[].field = "email"`. Returned in `CustomerResponse` (OD-004:A). |
| `enabled` | `enabled` | Internal account state; persisted but not exposed by US-001 responses (OD-004:A). |

No tokens, no other PII, no encryption-at-rest requirement introduced by this
Story.

## 8. Schema initialization

Consistent with the rewritten `persistence-conventions.md` PC-1, PC-2 and
`security-conventions.md` SC-8:

- Schema is defined via a **committed, reviewed EF Core Migration**
  (`dotnet ef migrations add AddCustomer --project CustomerPortal`), not
  hand-written SQL. The migration is generated *from* the
  `IEntityTypeConfiguration<Customer>` class (§8.2), reviewed like any other
  code change, and committed under `CustomerPortal/Data/Migrations/`.
- `Database.EnsureCreated()` / `EnsureDeleted()` are **forbidden** for this
  Story outside the isolated test database (PC-2, SC-8).
- Local/dev startup applies the migration via `Database.Migrate()`, gated
  behind the existing `Persistence:AutoMigrate` config flag
  (`CustomerPortal/Program.cs`, already scaffolded).
- Tests apply the **same** committed migration to an isolated in-memory
  SQLite database (`Data Source=:memory:`, one open connection per test
  class) rather than generating the schema from the current model — this is
  the EF Core equivalent of the old Hibernate `ddl-auto=validate` fail-fast
  check (PC-2).
- Database: file-based SQLite for local runs
  (`Data Source=./data/customer-portal.db`, already configured in
  `appsettings.json`); isolated in-memory SQLite for tests (PC-1). Generated
  `./data/*` files stay git-ignored (already in `.gitignore`).
- No database browser/admin UI is registered or exposed in any profile —
  unchanged by this Story (SEC-9, SC-6).

### 8.1 `IEntityTypeConfiguration<Customer>` (authoritative Fluent API for this Story)

Illustrative — the actual class lives at
`CustomerPortal/Data/Configurations/CustomerConfiguration.cs`
(`Data/Configurations/` already exists, currently empty):

```csharp
public class CustomerConfiguration : IEntityTypeConfiguration<Customer>
{
    public void Configure(EntityTypeBuilder<Customer> builder)
    {
        builder.ToTable("customer", t =>
            t.HasCheckConstraint("ck_customer_role", "role IN ('CUSTOMER','ADMIN')"));

        builder.HasKey(c => c.Id).HasName("pk_customer");

        builder.Property(c => c.Email)
            .HasMaxLength(254)
            .IsRequired();
        builder.HasIndex(c => c.Email)
            .IsUnique()
            .HasDatabaseName("uq_customer_email");

        builder.Property(c => c.PasswordHash)
            .HasMaxLength(60)
            .IsRequired();

        builder.Property(c => c.Role)
            .HasMaxLength(20)
            .IsRequired()
            .HasDefaultValue("CUSTOMER");

        builder.Property(c => c.Enabled)
            .IsRequired()
            .HasDefaultValue(true);

        builder.Property(c => c.CreatedAt).IsRequired();
        builder.Property(c => c.UpdatedAt).IsRequired();
    }
}
```

### 8.2 Illustrative migration `Up()` (generated, not hand-authored)

```csharp
migrationBuilder.CreateTable(
    name: "customer",
    columns: table => new
    {
        id = table.Column<long>(type: "INTEGER", nullable: false)
            .Annotation("Sqlite:Autoincrement", true),
        email = table.Column<string>(type: "TEXT", maxLength: 254, nullable: false),
        password_hash = table.Column<string>(type: "TEXT", maxLength: 60, nullable: false),
        role = table.Column<string>(type: "TEXT", maxLength: 20, nullable: false, defaultValue: "CUSTOMER"),
        enabled = table.Column<bool>(type: "INTEGER", nullable: false, defaultValue: true),
        created_at = table.Column<DateTimeOffset>(type: "TEXT", nullable: false),
        updated_at = table.Column<DateTimeOffset>(type: "TEXT", nullable: false)
    },
    constraints: table =>
    {
        table.PrimaryKey("pk_customer", x => x.id);
        table.CheckConstraint("ck_customer_role", "role IN ('CUSTOMER','ADMIN')");
    });

migrationBuilder.CreateIndex(
    name: "uq_customer_email",
    table: "customer",
    column: "email",
    unique: true);
```

Notes for `IMPLEMENTATION`:

- The actual migration file is generated by `dotnet ef migrations add`, not
  copied from this document — this snippet illustrates the expected shape so
  `IMPLEMENTATION_VERIFICATION` can check the generated file against it.
- `EFCore.NamingConventions` (already referenced in
  `CustomerPortal.csproj`, wired in `Program.cs` via
  `.UseSnakeCaseNamingConvention()`) is what turns C# `Email`/`PasswordHash`/
  `CreatedAt` into the `email`/`password_hash`/`created_at` columns shown
  above — the configuration class does not need to restate column names
  unless a name must diverge from that convention (none do here).
- Confirm after generation that `dotnet ef migrations add` actually reflects
  the check constraint (`HasCheckConstraint` requires the EF Core 7+ table
  builder overload used above) and the `INTEGER PRIMARY KEY AUTOINCREMENT`
  form for `id` under the SQLite provider.

## 10. Non-blocking findings for DESIGN_REVIEW

1. **Entity name** `Customer` / table `customer` chosen over glossary term
   `Account` for the credential representation; rationale in §3. Confirm
   (unchanged from v1).
2. **`role` as a `string` column with a CHECK constraint**, not a C# enum +
   value converter and not a `customer_role` table; rationale in §6. Confirm
   this is acceptable for the project's role model.
3. **`ck_customer_role` CHECK constraint** is a defensive addition not
   mandated by `persistence-conventions.md`; drop if the project prefers
   minimal DDL.
4. **`role` / `enabled` column `DEFAULT` values** are defensive for a manual
   write path only; the entity/service always sets both explicitly.
5. Password **72-byte** input limit (spec-review F-5 / API Q-4) is enforced
   in validation + service, not in the schema — `password_hash` is
   `TEXT, HasMaxLength(60)`. `TEST_WRITING` / `IMPLEMENTATION` own the
   72-byte boundary vector.
6. **New (v2):** confirm the EF Core check-constraint table-builder overload
   (`ToTable(t => t.HasCheckConstraint(...))`) generates correctly for the
   SQLite provider once `dotnet ef migrations add` actually runs — this was
   designed against documented EF Core 8 behavior but not yet exercised
   against this project's exact package versions (§8.1 note).
