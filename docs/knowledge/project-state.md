# Project State

Consolidated knowledge about what the Customer Portal application currently
does. Updated by `story-orchestrator` during **archive mode** (registry key
`project_state`), only after explicit human approval of the proposed changes.

Do not edit this file as part of a normal delivery stage — it reflects
*delivered and archived* capability, not work in progress.

## Delivered Capabilities

- **Customer self-service registration** (US-001, ASP.NET Core/EF Core/SQLite):
  `POST /api/v1/customers` creates a `Customer` (email, password hash via
  BCrypt, role) after FluentValidation checks (email format/length, password
  12-72 UTF-8 bytes, policy rules), rejecting duplicate emails with `409` and
  malformed bodies with `400`/`415`. Deny-by-default authorization (`SC-4`)
  is wired project-wide as the fallback policy. No authentication/login exists
  yet (see Known Constraints).

## Known Constraints

- Persistence: SQLite via EF Core Migrations, storage under `App_Data/`
  (moved from `data/` during US-001 to avoid a case-insensitive collision with
  the `Data/` source folder on Windows).
- No authenticated endpoint exists yet. `AddAntiforgery()` is registered but
  not enforced anywhere; cookie-auth's default 302-redirect challenge behavior
  has not been reconciled with `security-conventions.md` SC-3's 401
  requirement — relevant to US-002 Customer Login.
- Known Minor limitations carried from US-001: plaintext password visible in
  `RegistrationRequest`'s generated `ToString()`; 400/415 error message text
  differs from OpenAPI illustrative examples; concurrent duplicate
  registration can surface as `500` instead of `409` (anti-abuse/concurrency
  explicitly out of scope for US-001). Full detail:
  `docs/evidence/US-001-delivery-summary.md`.
